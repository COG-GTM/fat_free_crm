# fat-free-crm-api (Spring Boot)

Phase 1 foundation of the Rails -> Spring Boot strangler migration
(`docs/migration/migration-plan.md`). This module runs *alongside* Rails against
the same PostgreSQL database; it serves no production traffic yet.

## What exists today

| Area | State |
| --- | --- |
| Skeleton | `api`, `service`, `repository`, `domain`, `security`, `config` |
| Schema | Flyway `V1__baseline_rails_schema.sql`, dumped from a Rails-migrated database |
| Hibernate | `ddl-auto: validate` — Rails owns migrations until Phase 7 |
| Domain | `User`, `Group`, `Permission` only |
| Auth | `POST /api/v1/auth/login`, `POST /api/v1/auth/refresh`, `GET /api/v1/auth/me` |
| Contract | frozen Rails OpenAPI served at `/openapi.yaml` |
| Gateway | `gateway/nginx.conf` routes 100% to Rails, not yet deployed |

## Running

```bash
export FFCRM_DB_URL=jdbc:postgresql://localhost:5432/fat_free_crm_development
export FFCRM_DB_USER=postgres
export FFCRM_DB_PASSWORD=postgres
export FFCRM_JWT_SECRET="$(openssl rand -base64 48)"   # >= 32 bytes, required
./gradlew bootRun
```

Against a database Rails already migrated, Flyway baselines instead of replaying
V1 (`spring.flyway.baseline-on-migrate=true`), so an existing deployment is left
untouched.

## Checks

```bash
./gradlew build   # compile + test + checkstyle + spotbugs
```

Integration tests need Docker: Testcontainers starts PostgreSQL 14 (the ADR 0004
floor), applies Flyway, and lets Hibernate validate the mapping against it.

## Authentication notes

* Legacy Devise hashes (`authlogic_sha512`, per-user `password_salt`,
  20 stretches) are verified by `AuthlogicSha512PasswordEncoder`, checked
  byte-for-byte against hashes generated by the Rails app in
  `src/test/resources/fixtures/rails-legacy-users.json`.
* Hashes are never rewritten on login (`ffcrm.security.rehash-on-login=false`):
  Rails must keep being able to authenticate the same row.
* `password_salt` cannot travel through Spring's `PasswordEncoder.matches`
  contract, which is why `CrmAuthenticationProvider` replaces
  `DaoAuthenticationProvider`.
* Rails' `groups_users` join table stores `integer` keys against `bigint`
  primary keys, so membership is read with a native query rather than mapped as
  a JPA association.
